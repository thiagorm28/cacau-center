# ADR-002: Identificação de item por código de produto interno (cProd), com fallback manual e registro de divergência

## Status

Accepted

## Date

2026-08-16

## Context

O fluxo de conferência depende de comparar o código de barras físico bipado em cada caixa com os itens listados no XML da NFe. A expectativa inicial era usar o campo de EAN/GTIN (`cEAN`/`cEANTrib`) do XML para esse match. Uma nota real de exemplo (fornecedor IBAC, emissor das notas de produto Cacau Show) mostrou que esse campo vem preenchido como `"SEM GTIN"` — ou seja, não há GTIN/EAN oficial disponível para casar diretamente com o código de barras da caixa. O campo `cProd` (código interno do produto atribuído pelo fornecedor/ERP) é o identificador mais confiável disponível no XML para essa nota. Também ficou confirmado que a unidade comercial (`uCom`) do item já é a granularidade de caixa (ex: `CX`, com `qCom` = quantidade de caixas esperadas), então a conferência ocorre no nível de caixa, não de unidade individual dentro da caixa.

Como ainda não há confirmação de que o código de barras físico impresso na caixa sempre corresponderá exatamente a `cProd` (isso depende de como cada fornecedor rotula as caixas), o sistema precisa de um caminho de recuperação quando a bipagem não encontra correspondência automática.

## Decision

O sistema tenta casar o código bipado primeiro com `cProd` dos itens pendentes da(s) nota(s) em aberto (com `cEAN`/`cEANTrib` como campo alternativo de match, para fornecedores que preencherem GTIN corretamente no futuro). Quando nenhum item pendente corresponde ao código bipado, o app avisa que o código não foi reconhecido e oferece ao operador a opção de selecionar manualmente a qual item da nota aquela caixa pertence. Se o operador não conseguir identificar a caixa em nenhum item de nenhuma nota em aberto, ele pode registrá-la como "caixa extra/não identificada", que entra no relatório final daquela sessão de conferência para revisão posterior — sem bloquear o restante do fluxo.

## Alternatives Considered

### Alternative 1: Match exclusivo por EAN/GTIN

- **Description**: Confiar apenas no campo `cEAN`/`cEANTrib` do XML para identificar produtos.
- **Pros**: Padrão de mercado, mais robusto entre fornecedores diferentes.
- **Cons**: Não funciona para a nota de exemplo real, onde o campo vem como "SEM GTIN" — inviabilizaria a conferência para o fornecedor observado.
- **Why rejected**: Não cobre o caso real já identificado; `cProd` está sempre presente e é a alternativa viável confirmada pelo usuário.

### Alternative 2: Rejeitar silenciosamente bipagens sem correspondência

- **Description**: Ao não encontrar correspondência, apenas mostrar erro e não permitir nenhuma ação de recuperação (sem seleção manual, sem registro de divergência).
- **Pros**: Implementação mais simples.
- **Cons**: Deixa o operador sem saída quando o código de barras físico realmente não bate com nada no XML (situação que pode ser comum dado o `cEAN` ausente) — força ele a abandonar a conferência daquela caixa sem rastro.
- **Why rejected**: O usuário pediu explicitamente a combinação de seleção manual com fallback para "caixa extra/não identificada" no relatório.

## Consequences

### Positive

- A conferência funciona mesmo quando o fornecedor não preenche GTIN/EAN, que é o caso real já observado.
- Nenhuma caixa física fica "sem rastro" — toda bipagem sem match automático termina em uma ação do operador (seleção manual) ou num registro explícito de divergência.

### Negative

- Depender de `cProd` como chave primária de match assume que o código de barras impresso na caixa reflete esse campo; isso ainda precisa de validação física com uma caixa real antes da implementação (ver Open Questions no PRD).
- Seleção manual adiciona um passo de interação extra no fluxo quando o match automático falha.

### Risks

- Risco: se o código de barras físico da caixa não for nem `cProd` nem GTIN, mas outro identificador (ex: código de lote, código logístico), o match automático terá taxa de acerto baixa na prática. Mitigação: validar com uma caixa física antes de implementar, e manter o fallback manual como caminho sempre disponível.

## Implementation Notes

A definição exata de quais campos (`cProd`, `cEAN`, `cEANTrib`) e em que ordem de prioridade tentar o match, além da estrutura de leitura do XML, fica a cargo do TechSpec.
