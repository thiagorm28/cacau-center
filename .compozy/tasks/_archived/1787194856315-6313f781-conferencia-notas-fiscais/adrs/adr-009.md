# ADR-009: Sessão de autenticação curta (8h) via JWT em cookie httpOnly

## Status

Accepted

## Date

2026-08-16

## Context

O PRD (ADR-004) exige login individual por pessoa com papel associado (operador ou
gerente/dono). O usuário decidiu que a sessão deve durar o equivalente a um turno de
trabalho (cerca de 8h) em vez de sessões longas com renovação automática, priorizando
segurança sobre conveniência de nunca precisar logar de novo. Como o app funciona
offline durante a bipagem (ADR-003), o token de sessão precisa estar disponível
localmente mesmo sem conexão, mas a validação de que ele ainda é válido só ocorre contra
o backend quando há requisições de rede (busca de nota, sincronização).

## Decision

Autenticação via JWT assinado pelo backend (NestJS + `@nestjs/passport` com estratégia
JWT), token com expiração de 8h, entregue como cookie `httpOnly`, `Secure`,
`SameSite=Lax`. Não há refresh token nem renovação silenciosa: ao expirar, o operador
precisa autenticar novamente. O papel (`operador` | `gerente`) é uma claim no próprio
token, validada por um `RoleGuard` do NestJS em cada rota que exige um papel específico.
O frontend nunca lê o conteúdo do token diretamente (cookie `httpOnly` não é acessível
via JS); o estado de "autenticado como quem, com qual papel" é obtido via
`GET /auth/me` após o login e mantido em contexto de aplicação enquanto a sessão local
durar.

## Alternatives Considered

### Alternative 1: Token de acesso curto + refresh token de longa duração

- **Description**: Access token de vida curta renovado automaticamente por um refresh
  token de até 30 dias, evitando pedir login com frequência.
- **Pros**: Menos fricção para o operador.
- **Cons**: Contradiz a escolha explícita do usuário por sessão curta de turno de
  trabalho.
- **Why rejected**: O usuário preferiu sessão curta por segurança, mesmo com o custo de
  relogar mais vezes.

### Alternative 2: Token em `localStorage`, lido pelo frontend

- **Description**: Guardar o JWT em `localStorage` e anexá-lo manualmente em cada
  requisição via header `Authorization`.
- **Pros**: Mais simples de inspecionar/depurar no cliente.
- **Cons**: Exposto a XSS (qualquer script injetado no app consegue ler o token);
  cookie `httpOnly` remove essa superfície de ataque sem custo funcional adicional para
  este produto.
- **Why rejected**: Sem necessidade de acessar o token no cliente (o app só precisa
  saber "quem sou eu e qual meu papel", obtido via `/auth/me`), o cookie `httpOnly` é
  estritamente mais seguro pelo mesmo esforço de implementação.

## Consequences

### Positive

- Superfície de ataque menor (token não acessível via JavaScript no cliente).
- Modelo de sessão simples, sem lógica de renovação silenciosa para depurar.

### Negative

- Operador precisa logar novamente após 8h mesmo em uso contínuo, incluindo o caso de
  ter passado a maior parte do turno offline.

### Risks

- Risco: se a sessão expirar enquanto o operador está no meio de uma bipagem offline
  (sem conexão pra revalidar), o app não consegue confirmar a expiração até reconectar.
  Mitigação: bipagem offline continua funcionando localmente mesmo com token
  potencialmente expirado (ver ADR-003); a expiração só é aplicada quando uma requisição
  de rede de fato ocorre (ex: na sincronização), e o app pede novo login nesse momento
  sem descartar o progresso local já salvo.
