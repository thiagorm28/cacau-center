# ADR-004: Navigation drawer is embedded in the shared `Screen` component, self-deriving visibility from session state

## Status

Accepted

## Date

2026-08-20

## Context

The PRD (ADR-001) requires the drawer trigger to appear on every authenticated screen except the mandatory password-change screen, and nowhere else. The app has no shared layout wrapper — `App.tsx` uses a flat `<Routes>` with no `<Outlet>` or nested layout route — and every one of the 7 screens (including `LoginScreen`) already renders the shared `Screen` component (`frontend/src/components/ui/Screen.tsx`), which exposes a `header?: ReactNode` slot that each screen currently fills manually with `<LogoutButton />`.

`SessionUser` (from `api/types.ts`) already carries `mustChangePassword: boolean`, and `useSession()` exposes `status: "loading" | "authenticated" | "anonymous"`. Both are available anywhere inside the `SessionProvider` tree, which wraps the whole app including `LoginScreen`.

## Decision

`Screen` renders the drawer trigger button and the drawer itself internally. `Screen` calls `useSession()` and shows the trigger only when `status === "authenticated" && user !== null && !user.mustChangePassword`. This makes the trigger appear automatically on every authenticated screen without any new prop threaded through the 7 call sites — each screen only changes by removing its `header={<LogoutButton />}` (or equivalent) prop, since logout moves into the drawer per ADR-002. `LoginScreen` (status `"anonymous"`) and `ChangePasswordScreen` (`mustChangePassword === true`) naturally get no trigger, with no special-casing needed at their call sites.

## Alternatives Considered

### Alternative 1: New layout wrapper around `<Routes>`

- **Description**: Introduce an `AuthenticatedLayout` component wrapping authenticated routes via `<Outlet>`, rendering the trigger/drawer once outside `Screen`.
- **Pros**: Cleanly separates "layout chrome" from `Screen`'s current single responsibility (title/subtitle/content sheet).
- **Cons**: Requires introducing nested routes and `<Outlet>` into `App.tsx`, a routing pattern the app doesn't use today; a bigger structural change than the feature calls for.
- **Why rejected**: User rejected this in favor of the `Screen`-embedded approach — no reason to introduce a new routing pattern for a self-contained UI feature.

### Alternative 2: Each screen wires the drawer manually

- **Description**: Every screen imports and renders `<NavDrawer />` explicitly, mirroring today's `LogoutButton` pattern.
- **Pros**: No change to `Screen`'s responsibilities.
- **Cons**: Replicates wiring across 7 call sites, the exact duplication problem ADR-002 is trying to eliminate for logout.
- **Why rejected**: User explicitly chose centralizing in `Screen` over replicating per-screen wiring.

## Consequences

### Positive

- Zero new props on `Screen`'s public API; the drawer "just works" everywhere `Screen` is already used.
- Impossible for a new screen to forget to add the trigger — it comes for free from using `Screen`.

### Negative

- `Screen` gains a dependency on `useSession()` and takes on a second responsibility (layout chrome + now navigation chrome), where before it only rendered title/subtitle/content.

### Risks

- If a future screen legitimately needs `Screen` without the drawer (none identified today), this would require a new opt-out prop. Not a concern for the current scope.

## Implementation Notes

`Screen` renders `<NavDrawer />` (new component, see ADR-005/ADR-006) unconditionally; `NavDrawer` itself performs the `useSession()` visibility check internally rather than `Screen` conditionally rendering it, so the check lives in one place.
