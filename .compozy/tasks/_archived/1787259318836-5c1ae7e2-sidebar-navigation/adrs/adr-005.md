# ADR-005: Extract a single shared route/role registry consumed by routing and the navigation drawer

## Status

Accepted

## Date

2026-08-20

## Context

Today the role required for each top-level route is duplicated: `App.tsx` passes a literal role string (`"operador"`, `"gerente"`, `"admin"`) to `<RequireRole role="...">` at each `<Route>`, and the same three roles are re-derived inline for the post-login home redirect (`user.role === "operador" ? "/notas" : ...`). The navigation drawer (ADR-003) needs the same path→label→role mapping to decide which items to show. Adding a fourth, independent copy of this mapping inside the drawer would create a third (soon fourth) place that must be kept in sync by hand — exactly the drift risk ADR-003 flagged as a real trade-off.

## Decision

Introduce `frontend/src/routes/navigation.ts` as the single source of truth for the three top-level features: path, human-readable label, and the role required to access it (admin's existing all-access bypass stays in `RequireRole`, unchanged). It exports:

- `NAV_ROUTES: readonly NavRouteItem[]` — ordered list of `{ path, label, role }` for the three top-level features, consumed directly by the drawer's navigation list.
- Named path/role constants (or a lookup keyed by role) derived from `NAV_ROUTES`, consumed by `App.tsx` in place of today's literal role strings on `<RequireRole role="...">`, and by the home-redirect logic in place of the inline ternary.

`App.tsx`, `RequireRole` usage sites, and the drawer's nav list all read from this one module. Sub-flow routes (bipagem, relatório) and the change-password route are NOT part of `NAV_ROUTES` — they stay declared directly in `App.tsx` as today, since they are not top-level navigation destinations (ADR-003).

## Alternatives Considered

### Alternative 1: Small config local to the drawer, mirrored by hand

- **Description**: A drawer-local `NAV_ITEMS` array duplicating the role literals already in `App.tsx`, with a test asserting the two stay in sync.
- **Pros**: Zero changes to existing, working routing code.
- **Cons**: A test catching drift is a safety net, not a fix — the duplication itself remains and can still be edited inconsistently between the two edits of the same PR.
- **Why rejected**: User chose eliminating the duplication over minimizing the diff to existing routing code.

## Consequences

### Positive

- One place defines "which top-level features exist, at which path, requiring which role" — routing, redirect logic, and the drawer all read the same data, so they cannot drift.
- Adding or renaming a top-level feature in the future is a one-file change instead of a three-place change.

### Negative

- Touches `App.tsx`, a file that works today, to replace inline role literals with references into `navigation.ts` — a refactor of existing, tested code as part of this feature.

### Risks

- Regression risk in `App.tsx`'s routing during the refactor; mitigated by the existing route/role test coverage (e.g. `RequireRole.test.tsx`) continuing to pass unchanged, since the *values* don't change, only where they're read from.

## Implementation Notes

`RequireRole.tsx` itself is unchanged — it still receives a `role` prop and still special-cases admin bypass; only the *call sites* in `App.tsx` change what they pass.
