# ADR-003: Drawer navigation list is scoped to top-level features by role, excluding account-action routes

## Status

Accepted

## Date

2026-08-20

## Context

The app already enforces role-based route access via `RequireRole` (`frontend/src/routes/RequireRole.tsx`): `operador` reaches `/notas*`, `gerente` reaches `/historico`, `admin` reaches `/usuarios` and bypasses every role check (reaches everything). Existing routes split into two kinds: top-level features a user chooses to go to (fila de notas, histórico, gestão de usuários) and drill-down/sub-flow screens reached from within a feature (bipagem, relatório of a specific note) or forced/account-action screens (`/trocar-senha`, only reachable today via the mandatory `RequirePasswordChange` redirect, with no existing voluntary entry point anywhere in the app).

## Decision

The drawer's navigation list shows only top-level features the current user's role can access — fila de notas, histórico, gestão de usuários, filtered by the same role logic `RequireRole` already enforces. Drill-down screens (bipagem, relatório) are not listed, since they only make sense in the context of a specific note reached by drilling in from fila de notas. `/trocar-senha` is not listed either — it remains reachable only through the mandatory forced-change flow, unchanged from today's behavior, so this decision introduces no regression (confirmed by codebase search: no voluntary entry point to change-password exists today). The drawer additionally shows the logged-in user's name and role at the top, and the logout action at the bottom (ADR-002); the current screen's feature, if present in the list, is visually indicated as active.

## Alternatives Considered

### Alternative 1: Include "Trocar senha" as a navigable item

- **Description**: Add a voluntary "Trocar senha" entry to the drawer nav list alongside the three top-level features.
- **Pros**: Gives users a voluntary path to change their password, which doesn't exist today.
- **Cons**: Expands scope beyond what was requested; introduces new behavior (voluntary password change) that has its own edge cases not yet explored.
- **Why rejected**: User explicitly scoped the drawer to top-level business features only; voluntary password change is a separate, unrequested capability.

## Consequences

### Positive

- Drawer stays focused and short — no clutter from sub-flow or account-action routes that don't belong in a "jump to a feature" list.
- Reuses `RequireRole`'s existing role logic instead of introducing a second source of truth for who sees what.

### Negative

- Single-feature roles (`operador`, `gerente`) will see a drawer with only one navigable item besides their own profile/logout — the drawer's main value for them is consistent logout access and identity display, not multi-feature navigation.

### Risks

- None beyond the negative above; accepted as inherent to the current role model.

## Implementation Notes

Product-level only; how the nav list is derived from `RequireRole`'s logic (shared helper vs. duplicated mapping) belongs to the TechSpec.
