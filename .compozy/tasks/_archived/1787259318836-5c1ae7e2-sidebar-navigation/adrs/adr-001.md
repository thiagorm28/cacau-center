# ADR-001: Global overlay navigation drawer, triggered from every authenticated screen

## Status

Accepted

## Date

2026-08-20

## Context

The app has no shared shell or header — each screen is a standalone `Screen` component with its own chocolate-colored header. There is no way today for a user to move between top-level features (fila de notas, histórico, gestão de usuários) except by using the browser/back navigation or being redirected by role on `/`. The app is a mobile-only PWA (portrait-only, standalone display, zero responsive breakpoints), so any new navigation surface must work as a single-column, touch-first pattern rather than a desktop persistent sidebar.

The closest existing UI precedent is `Dialog.tsx`: a bottom-anchored overlay sheet with a `bg-choc-800/60` scrim. Market research on sidebar navigation confirms that for mobile-only apps, an off-canvas overlay drawer (slide-in from an edge, with a backdrop) is the standard pattern, distinct from the persistent icon-rail sidebars used on desktop admin dashboards.

## Decision

Add a retractable side navigation drawer, opened by a trigger button placed consistently in the header of every authenticated screen (fila de notas, bipagem, relatório, histórico, gestão de usuários) with two exceptions: the login screen (unauthenticated, nothing to navigate to) and the mandatory password-change screen (per ADR-002-adjacent scope decision, navigation must not let the user escape a required password change).

The drawer is a left-anchored overlay sheet, mirroring `Dialog.tsx`'s scrim + sheet pattern (dark backdrop over the current screen, sheet slides in from the edge rather than pushing content). It closes when the user: taps/navigates to a destination, taps the darkened backdrop outside the sheet, or swipes the sheet back off-screen. The drawer's open/closed state does not persist across page reloads — it always starts closed.

## Alternatives Considered

### Alternative 1: Persistent icon-rail sidebar (desktop admin pattern)

- **Description**: Always-visible collapsible sidebar that narrows to icons, as in Ant Design's `Sider`.
- **Pros**: Familiar pattern for admin tools; no open/close interaction needed.
- **Cons**: Assumes horizontal space the mobile-only, portrait-locked layout doesn't have; would permanently eat into an already narrow viewport.
- **Why rejected**: Inconsistent with the app's mobile-only, single-column design and DESIGN.md's full-bleed sheet layouts.

### Alternative 2: Trigger button only on top-level "home" screens

- **Description**: Show the drawer trigger only on fila de notas, histórico, and gestão de usuários — not on sub-flow screens like bipagem or relatório.
- **Pros**: Slightly less header clutter on deep, focused flows.
- **Cons**: Breaks the core promise of "navigate between funcionalidades from anywhere"; also removes the user's only path to logout from those sub-flow screens once logout moves into the drawer (ADR-002).
- **Why rejected**: User explicitly chose global placement on every authenticated screen.

## Consequences

### Positive

- Users get one consistent, predictable way to switch features and log out, regardless of which screen they're on.
- Reuses an established visual pattern (`Dialog.tsx` scrim + sheet), keeping implementation and visual language consistent with DESIGN.md.

### Negative

- Every authenticated screen's header now needs to reserve space for a trigger button, a layout change across 7 screens.

### Risks

- No icon library exists in the frontend today; the trigger icon must be added (inline SVG or a small icon set) — flagged for TechSpec, not a product blocker.

## Implementation Notes

Product-level only: exact trigger icon, animation timing, and component structure are TechSpec concerns.
