# ADR-005: Corte de acesso imediato via store de revogação em memória

## Status

Accepted

## Date

2026-08-19

## Context

O JWT de sessão hoje é totalmente stateless: `JwtStrategy.validate`
(`backend/src/infra/auth/JwtStrategy.ts:26-33`) só decodifica o payload assinado, sem
nenhuma consulta ao banco. O token vive até 8h (`SESSION_TTL_SECONDS`,
`backend/src/domain/SessionUser.ts:12`).

O ADR-003 exige que desativar um usuário corte o acesso de uma sessão já aberta
imediatamente, não apenas na próxima tentativa de login (PRD, Business Rules: "uma
sessão já aberta no momento da desativação perde o acesso"; US-007.AC-2/EC-1). Um JWT
puramente stateless não permite isso: o token continuaria válido até expirar sozinho.

O deploy atual (`docker-compose.yaml`) é single-instance — um único container de
backend, sem Redis nem outro cache compartilhado.

## Decision

Um `SessionRevocationStore` em memória (singleton do processo Nest, registrado como
provider em `AuthModule` e exportado) mantém um `Map<userId, revokedAtMs>`. O usecase
`DeactivateUser` chama `revoke(userId)` ao desativar um usuário, gravando o timestamp
atual. Uma nova checagem no fluxo de autenticação (dentro de `JwtStrategy.validate` ou
um guard logo em seguida ao `AuthGuard`) compara o `iat` (issued-at, em segundos,
adicionado automaticamente pelo `@nestjs/jwt` a cada token) do payload contra o
`revokedAtMs` do usuário: se o token foi emitido antes da revogação, a request é
recusada com `UnauthorizedError` (401), forçando novo login. Reativar um usuário não
precisa limpar a entrada — qualquer token novo emitido após a reativação já tem `iat`
posterior ao `revokedAtMs` registrado, então passa a checagem naturalmente.

Este mesmo store não é usado para a troca de senha obrigatória (ADR-002) — ver
Implementation Notes.

## Alternatives Considered

### Alternative 1: Consulta ao banco a cada request autenticado

- **Description**: `JwtStrategy.validate` passaria a buscar a linha do usuário
  (`active`) no banco a cada request, em vez de manter estado em memória.
- **Pros**: Sem estado em memória para gerenciar; sobrevive a restart do processo sem
  perder informação de revogação.
- **Cons**: Adiciona uma consulta ao banco em todo request autenticado do sistema
  (bipagem, histórico, gestão de usuários), inclusive nos de maior volume.
- **Why rejected**: Descartada por decisão explícita do usuário durante o grilling
  técnico, em favor de manter o caminho de autenticação sem I/O de banco extra por
  request.

### Alternative 2: Blacklist em cache compartilhado (Redis)

- **Description**: Store de revogação em Redis (ou equivalente), consultado a cada
  request, sobrevivendo a restart do processo e preparado para múltiplas instâncias de
  backend.
- **Pros**: Resiliente a restart; funcionaria corretamente se o backend um dia escalar
  horizontalmente.
- **Cons**: Introduz um componente de infraestrutura novo (serviço Redis no
  `docker-compose.yaml` de dev/prod/e2e, client novo no backend) só para este caso —
  não há nenhum outro uso de cache compartilhado no sistema hoje.
- **Why rejected**: O deploy é single-instance; o ganho de resiliência a restart não
  justifica o novo componente de infra para uma loja única. Se o backend algum dia
  precisar escalar horizontalmente, esta ADR pode ser revisitada.

### Alternative 3: Aceitar janela de até 8h sem corte imediato

- **Description**: Manter o JWT totalmente stateless; desativação só bloqueia logins
  futuros, sessão já aberta continua válida até expirar.
- **Pros**: Zero mudança no mecanismo de autenticação atual.
- **Cons**: Contradiz diretamente a regra de negócio já escrita no PRD e o critério
  US-007.AC-2/EC-1 — um funcionário desligado continuaria acessando o sistema por até
  8h.
- **Why rejected**: Chegou a ser cogitada durante o grilling técnico, mas rejeitada ao
  confrontar explicitamente com o texto do PRD; o usuário confirmou manter o corte
  imediato.

## Consequences

### Positive

- Corte de acesso imediato para contas desativadas, sem I/O de banco extra por
  request e sem novo componente de infraestrutura.
- Reativação funciona sem nenhuma lógica adicional de limpeza — é uma propriedade
  natural da comparação por timestamp.

### Negative

- Estado de revogação vive só na memória do processo backend — não é compartilhável
  se o backend algum dia rodar em múltiplas instâncias sem sticky routing.

### Risks

- **Restart do processo perde o estado de revogação**: um usuário desativado antes do
  restart, cujo token ainda não expirou, volta a ter acesso até uma nova ação de
  escrita (redesativação) ou até o token expirar naturalmente (máx. 8h). Aceito
  explicitamente pelo usuário durante o grilling técnico como risco tolerável na escala
  de uma única loja — mitigação: nenhuma ação automática necessária; documentado aqui
  para referência futura caso o volume/criticidade do sistema mude.

## Implementation Notes

- O mesmo mecanismo **não** cobre a troca de senha obrigatória (ADR-002): esse estado é
  carregado como claim `mustChangePassword` no próprio payload do JWT, decidido no
  momento do login (lido do banco pelo usecase `Login`) e reemitido (`false`) quando o
  usecase `ChangeInitialPassword` conclui com sucesso — não precisa de estado
  compartilhado entre requests porque é reavaliado a cada emissão de token, e o cenário
  de reset de senha durante uma sessão já aberta não está no escopo de nenhum
  critério de aceite desta feature.
- O `SessionRevocationStore` expõe uma interface mínima: `revoke(userId: string): void`
  e `isRevoked(userId: string, tokenIssuedAtSeconds: number): boolean`.
