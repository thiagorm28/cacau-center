# ADR-003: Desativação em vez de exclusão de usuários

## Status

Accepted

## Date

2026-08-19

## Context

O admin precisa poder remover o acesso de um usuário que saiu da loja (parte do CRUD
completo pedido para a tela de gestão de usuários). No schema atual, `invoiceNotes`
referencia o usuário que abriu a nota (`openedBy`) e `scanEvents` referencia quem
registrou cada bipagem (`scannedBy`) — ou seja, todo histórico operacional já
implementado depende da linha do usuário continuar existindo.

## Decision

Remover acesso de um usuário é uma desativação lógica (ex.: flag `ativo`/`inativo`),
nunca uma exclusão da linha. Uma conta desativada não consegue mais logar, mas seu
nome continua aparecendo corretamente no histórico de notas e no relatório de
divergência já existentes. O admin pode reverter a desativação (reativar) a qualquer
momento pela mesma tela.

## Alternatives Considered

### Alternative 1: Exclusão definitiva (hard delete)

- **Description**: `DELETE` da linha do usuário ao removê-lo.
- **Pros**: Nenhum estado extra para gerenciar; a lista de usuários só mostra quem
  está ativo.
- **Cons**: Quebra a integridade referencial com `invoiceNotes.openedBy` e
  `scanEvents.scannedBy` (ou exige `ON DELETE SET NULL`, que apaga do histórico
  quem fez o quê) — o histórico gerencial existente (US-016/US-017 do produto de
  conferência de notas) depende de saber quem abriu/bipou cada nota.
- **Why rejected**: Apagaria informação que o produto já promete ao gerente/dono
  (rastreabilidade de quem fez cada conferência), só para economizar um campo booleano.

## Consequences

### Positive

- Histórico de notas e relatórios de divergência continuam íntegros e atribuídos
  corretamente mesmo depois que um funcionário sai.
- Reverter uma desativação por engano é trivial (não é uma recriação de conta).

### Negative

- A tabela de usuários acumula contas inativas indefinidamente (sem rotina de
  limpeza) — aceitável dado o volume esperado (poucos funcionários por loja).

### Risks

- Login de conta desativada precisa ser bloqueado tanto na autenticação quanto na
  validação da sessão já emitida (um JWT emitido antes da desativação não deve
  continuar válido até expirar sozinho) — detalhe de enforcement fica para o
  TechSpec, mas a exigência de produto é: desativar corta acesso imediatamente.

## Implementation Notes

Mecanismo exato de invalidar sessões já emitidas (checar flag a cada request vs.
revogar token) é decisão de TechSpec.
