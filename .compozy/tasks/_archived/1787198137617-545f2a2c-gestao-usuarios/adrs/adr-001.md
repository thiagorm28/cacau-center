# ADR-001: Papel admin único, provisionado fora da aplicação

## Status

Accepted

## Date

2026-08-19

## Context

O produto hoje tem dois papéis (`operador`, `gerente`), ambos criados manualmente no
banco — não existe nenhuma rota, tela ou script de criação de usuário. O pedido é
introduzir um papel `admin` com acesso irrestrito ao sistema, do qual só existirá uma
conta durante toda a vida do produto (é o dono/responsável pela loja, não um papel
operacional recorrente).

Isso levanta um problema de ovo-e-galinha: a nova tela de cadastro de usuários só pode
ser acessada por um admin, mas alguém precisa criar o primeiro (e único) admin antes de
qualquer tela existir para isso.

## Decision

A conta admin é criada por um script de bootstrap executado uma única vez na
implantação (seed/migration), lendo nome, e-mail e senha de variáveis de ambiente (ou
gerando uma senha aleatória se não informada). Não existe nenhuma rota de API, tela ou
botão na aplicação capaz de criar uma segunda conta admin — o papel `admin` nunca
aparece como opção selecionável na tela de cadastro de usuários (essa tela só cria
`operador`/`gerente`). Se um dia for necessário trocar a conta admin, isso acontece por
intervenção direta no banco/infra, não por um fluxo de produto.

## Alternatives Considered

### Alternative 1: Assistente de primeiro acesso (setup wizard)

- **Description**: Ao subir o sistema sem nenhum admin cadastrado, a própria aplicação
  mostra uma tela de configuração inicial para criar a conta admin no primeiro acesso.
- **Pros**: Não depende de acesso a variáveis de ambiente/infra; quem sobe o sistema
  pode ser alguém sem acesso técnico ao servidor.
- **Cons**: Exige manter, para sempre, uma rota pública de "criar admin se nenhum
  existir" — superfície de ataque permanente (quem chegar primeiro nessa rota vira
  admin). Mais código de produto para um evento que acontece uma vez na vida do sistema.
- **Why rejected**: O ganho de UX não compensa manter uma rota sensível
  permanentemente disponível; o script de bootstrap resolve o mesmo problema sem essa
  superfície.

## Consequences

### Positive

- Nenhuma rota de produto expõe criação de admin — a tela de cadastro de usuários
  nunca precisa lidar com esse caso.
- O papel admin fica claramente fora do ciclo de vida normal de usuários (que é
  CRUD via a tela nova).

### Negative

- Recriar/rotacionar a conta admin exige acesso à infra (banco ou variáveis de
  ambiente), não é self-service dentro do produto.

### Risks

- Se o script de bootstrap rodar mais de uma vez sem checar existência prévia, pode
  duplicar/sobrescrever a conta admin — o script deve ser idempotente (checar se já
  existe um admin antes de criar).

## Implementation Notes

Detalhamento do script (linguagem, onde roda no pipeline de deploy, formato das
variáveis de ambiente) é decisão de TechSpec.
