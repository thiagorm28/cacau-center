# ADR-005: `DELETE /notes/:id` como primeiro endpoint DELETE do projeto

## Status

Accepted

## Date

2026-08-22

## Context

Toda rota de ação do projeto hoje é `POST` com sufixo (`/users/:id/deactivate`,
`/users/:id/reactivate`, `/notes/:id/finalize`), porque até agora toda ação era uma
transição de estado (desativar, reativar, finalizar), nunca uma destruição física de
registro. A exclusão de nota (ADR-001 do PRD) é a primeira operação do sistema que
apaga uma linha de verdade, então era preciso decidir se ela seguiria o mesmo padrão de
rota de ação ou usaria o verbo HTTP semanticamente correto para destruição.

O cliente HTTP do frontend (`frontend/src/api/client.ts`) hoje só tem helpers `post`/`patch`/`request`
genérico — nenhuma chamada usa `DELETE` ainda.

## Decision

O endpoint de exclusão é `DELETE /notes/:id`, retornando `204 No Content` (o `request()`
do client já trata `204` como corpo vazio, sem mudança necessária nesse tratamento). O
`NoteController` ganha um método `delete` decorado com `@Roles("operador")` e `@Delete(":id")`,
reaproveitando o `noteIdParam()` (`ParseUUIDPipe` com `NotFoundError`) já usado nas
demais rotas de nota. O client ganha um helper novo:

```ts
const del = <T>(path: string): Promise<T> => request<T>(path, { method: "DELETE" });

export const deleteNote = (noteId: string): Promise<void> => del<void>(`/notes/${noteId}`);
```

## Alternatives Considered

### Alternative 1: `POST /notes/:id/delete`

- **Description**: Seguir exatamente o padrão de rota de ação já usado por
  `deactivate`/`reactivate`/`finalize`, evitando introduzir um verbo HTTP novo no
  projeto.
- **Pros**: Zero mudança de infraestrutura no client (`post<T>` já existe e cobre o
  caso); consistente por analogia com as outras rotas de ação existentes.
- **Cons**: Semanticamente incorreto — não é uma transição de estado, é destruição
  definitiva do registro; para um endpoint que já não tem volta, `DELETE` comunica isso
  de forma mais direta a quem lê a API depois.
- **Why rejected**: O usuário preferiu o verbo REST correto, aceitando o custo pequeno
  de adicionar um helper `del<T>` ao client.

## Consequences

### Positive

- Semântica HTTP correta para uma operação destrutiva e irreversível.
- Não colide com nenhuma rota existente de nota.

### Negative

- Primeira rota `DELETE` do projeto — qualquer middleware/proxy/CORS que hoje só espere
  `GET`/`POST`/`PATCH` precisa ser conferido (mitigado: `Caddyfile`/CORS do backend não
  filtram por verbo hoje, ver TechSpec).

### Risks

- Nenhum risco técnico relevante além da checagem de infraestrutura acima.
