# ADR-006: Comparador de conclusão extraído de `resolveScan` para `shared`, reaproveitado pelo atalho de bipagem rápida

## Status

Accepted

## Date

2026-08-22

## Context

O atalho de bipagem rápida (US-005) precisa escolher, entre as notas abertas
carregadas na fila, a que tem maior percentual de conclusão (`confirmedTotal / expectedTotal`),
com empate resolvido pela nota aberta há mais tempo — exatamente a mesma técnica de
comparação já usada dentro de `resolveScan` (`shared/src/allocation/resolveScan.ts`,
função interna `isBetterCandidate`): comparação cruzada (`a.confirmado * b.esperado`
vs. `b.confirmado * a.esperado`) para evitar erro de ponto flutuante, com
`parseOpenedAt` tratando timestamp inválido como "infinitamente recente" para nunca
vencer o desempate.

O PRD deixa explícito que o algoritmo de alocação de bipagem (`resolveScan`) em si não
muda de comportamento — só o ponto de entrada da tela muda (ADR-002 do PRD). A questão
técnica era só onde colocar essa segunda necessidade da mesma técnica de comparação: uma
cópia independente no frontend, ou uma extração da técnica para `shared`, reaproveitada
tanto pelo `resolveScan` (que já a usa) quanto pela nova função do atalho.

## Decision

A técnica de comparação e desempate é extraída para um módulo novo,
`shared/src/allocation/completionOrder.ts`, interno ao pacote `shared` (não exportado na
raiz do pacote):

```ts
export interface CompletionCandidate {
  readonly confirmedQty: number;
  readonly totalExpected: number;
  readonly openedAtMs: number;
}

export const parseOpenedAt = (openedAt: string): number => {
  const parsed = Date.parse(openedAt);
  return Number.isNaN(parsed) ? Number.POSITIVE_INFINITY : parsed;
};

export const isCloserToCompletion = (
  candidate: CompletionCandidate,
  incumbent: CompletionCandidate,
): boolean => {
  const candidateRatio = candidate.confirmedQty * incumbent.totalExpected;
  const incumbentRatio = incumbent.confirmedQty * candidate.totalExpected;
  if (candidateRatio !== incumbentRatio) return candidateRatio > incumbentRatio;
  return candidate.openedAtMs < incumbent.openedAtMs;
};
```

`resolveScan.ts` passa a importar `isCloserToCompletion`/`parseOpenedAt` desse módulo em
vez de manter sua própria cópia local (`isBetterCandidate` vira um adaptador fino que
monta `CompletionCandidate` a partir de `ScanCandidate` e delega) — extração mecânica,
sem alterar nenhum resultado: os testes existentes (`resolveScan.test.ts`, UT-003)
continuam validando o comportamento exato.

Uma nova função, `pickQuickScanNote`, em `shared/src/allocation/pickQuickScanNote.ts`,
usa o mesmo comparador sobre os totais já agregados de cada nota (`NoteView.confirmedTotal`/`expectedTotal`
no frontend, sem precisar do detalhamento por item que `resolveScan` exige):

```ts
export interface OpenNoteSummary {
  readonly noteId: string;
  readonly openedAt: string;
  readonly confirmedTotal: number;
  readonly expectedTotal: number;
}

export function pickQuickScanNote(openNotes: readonly OpenNoteSummary[]): string | null;
```

`pickQuickScanNote` e `OpenNoteSummary` são exportados na raiz de `shared` (`shared/src/index.ts`);
`completionOrder.ts` continua interno ao pacote.

## Alternatives Considered

### Alternative 1: Função independente só no frontend, sem tocar em `shared`

- **Description**: Reimplementar a mesma técnica de comparação cruzada/desempate direto
  em `frontend/src`, sem nenhuma mudança em `resolveScan.ts` ou no pacote `shared`.
- **Pros**: Zero risco para `resolveScan` e seus testes existentes; menor blast radius,
  já que `shared` é consumido tanto pelo backend quanto pelo frontend.
- **Cons**: Duplica a técnica de comparação cruzada e o tratamento de `openedAt`
  inválido em dois lugares que precisam continuar concordando — uma mudança futura no
  critério de desempate exigiria lembrar de replicar nos dois.
- **Why rejected**: O usuário preferiu explicitamente reaproveitar a lógica já existente
  via `shared`, evitando a duplicação, mesmo com o custo de tocar num pacote consumido
  pelo backend.

## Consequences

### Positive

- Nenhuma duplicação da técnica de comparação cruzada/desempate entre backend e
  frontend.
- `resolveScan.ts` fica mais enxuto (delega a comparação), sem mudar seu contrato
  externo nem seu comportamento testado.

### Negative

- Uma mudança de schema pequena em `shared` (novo arquivo, refatoração interna de
  `resolveScan.ts`) passa a fazer parte do escopo deste PRD, mesmo ele tendo declarado
  que o algoritmo de alocação não muda — mitigado pela extração ser estritamente
  mecânica e coberta pelos testes já existentes de `resolveScan`.

### Risks

- Risco: um erro na extração alterar sutilmente o resultado de `resolveScan` (ex.:
  trocar `>` por `>=`, inverter a ordem dos argumentos). Mitigação: `resolveScan.test.ts`
  (UT-003 e os demais) deve passar sem nenhuma alteração de asserção — qualquer mudança
  neles durante a implementação é sinal de regressão de comportamento, não de teste
  desatualizado.
