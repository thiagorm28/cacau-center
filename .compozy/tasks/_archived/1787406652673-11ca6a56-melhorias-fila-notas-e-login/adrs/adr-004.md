# ADR-004: Exclusão em cascata orquestrada no usecase, sem `ON DELETE CASCADE` no schema

## Status

Accepted

## Date

2026-08-22

## Context

A exclusão de nota (ADR-001 do PRD) precisa apagar, de forma consistente, três tabelas:
`invoice_notes`, `note_items` (FK `note_id → invoice_notes.id`) e `scan_events` (FKs
nullable `note_id → invoice_notes.id` e `note_item_id → note_items.id`). Hoje nenhuma
FK do schema tem `onDelete: "cascade"` configurado — todas usam o padrão `no action` do
Drizzle, inclusive as de `scan_events`, que são nullable de propósito (bipagens
`unidentified` ficam sem nota até serem "reivindicadas" por `claimUnidentified`).

Havia duas formas de fazer o Postgres apagar os três registros de forma atômica: deixar
o banco cascatear via `ON DELETE CASCADE` nas FKs, ou o usecase apagar explicitamente
nas três tabelas dentro da mesma transação do `UnitOfWork` — o mesmo padrão que
`FinalizeNote` já usa para orquestrar `notes.close()` e `scanEvents.claimUnidentified()`
numa única transação.

## Decision

`DeleteNote` (novo usecase) apaga explicitamente, dentro de uma única
`unitOfWork.run(...)`, primeiro os `scan_events` da nota (`ScanEventRepository.deleteByNoteId`),
depois a nota e seus itens (`NoteRepository.delete`, que remove `note_items` e depois a
linha de `invoice_notes` na mesma chamada). Nenhuma FK do schema ganha `onDelete: "cascade"`
— o schema Drizzle permanece como está, sem migration de constraint.

Ordem de exclusão obrigatória (por causa das FKs existentes, sem cascade):
`scan_events` → `note_items` → `invoice_notes`.

## Alternatives Considered

### Alternative 1: `ON DELETE CASCADE` nas FKs de `note_items` e `scan_events`

- **Description**: Adicionar `{ onDelete: "cascade" }` às três FKs relevantes e deixar
  o Postgres apagar `note_items`/`scan_events` automaticamente ao apagar a linha de
  `invoice_notes` — o usecase só precisaria de um `DELETE FROM invoice_notes WHERE id = ...`.
- **Pros**: Menos código no usecase; garante a cascata mesmo se outro caminho de código
  algum dia apagar uma nota sem passar pelo usecase.
- **Cons**: Seria a primeira FK do projeto com cascade — muda o comportamento padrão de
  exclusão para qualquer código futuro que apague uma linha de `invoice_notes`, inclusive
  por engano; exige uma migration nova alterando constraints existentes; menos explícito
  sobre o que realmente é apagado, dificultando auditar a operação nos testes de unidade
  (que usam repositórios em memória, não o Postgres real).
- **Why rejected**: O usuário optou pela orquestração explícita no usecase, seguindo o
  padrão já estabelecido por `FinalizeNote` no projeto, e evitando introduzir cascade
  automático num schema que hoje é deliberadamente `no action` em toda parte.

## Consequences

### Positive

- Nenhuma mudança de schema/migration é necessária para este PRD.
- O comportamento de exclusão fica inteiramente no código da aplicação, testável com os
  repositórios em memória (`InMemoryNoteRepository`/`InMemoryScanEventRepository`) do
  jeito que `FinalizeNote.test.ts` já testa orquestração multi-repositório.
- Consistente com o padrão de UnitOfWork já documentado (ADR-007 de um PRD anterior):
  leitura e escrita relacionadas ficam na mesma transação.

### Negative

- Qualquer futuro caminho de código que precise apagar uma nota (hoje só existe este)
  precisa lembrar de repetir a mesma ordem de três exclusões — não há uma garantia do
  banco que torne isso automático.

### Risks

- Risco: esquecer a ordem correta (`scan_events` antes de `note_items` antes de
  `invoice_notes`) quebraria a FK e falharia a transação inteira (o que é seguro — a
  falha reverte tudo, não deixa exclusão parcial) — mas é um detalhe de implementação que
  o TechSpec precisa deixar explícito para quem implementar.

## Implementation Notes

`NoteRepository` ganha um método `delete(noteId: string): Promise<void>` que apaga
`note_items` e depois a linha de `invoice_notes` (o mesmo repositório já mexe nas duas
tabelas em `create`). `ScanEventRepository` ganha `deleteByNoteId(noteId: string): Promise<number>`.
Ambas as interfaces precisam de implementação correspondente em
`backend/test/support/InMemoryRepositories.ts` para os testes de unidade continuarem
compilando.
